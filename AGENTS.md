## 1. The rules that matter most

1. **Never modify anything under the frozen paths:** `docs/contracts/` and every merged migration in `apps/api/drizzle/` (`0000`–`0013` and their `meta/` snapshots). These are shared interfaces other agents build against. If one looks wrong, **stop and report it**; a unilateral change silently breaks another agent's work.
2. **Stay inside your Task's directories** (§4), plus its tests. If the work seems to need a file elsewhere, stop and ask.
3. **Agents never push or merge.** The founder owns `main` in both repos, pushes, opens PRs and merges.
4. **Never paste or print a secret** (keys, tokens, passwords, connection strings with credentials, PEM material, Supabase keys) into a chat, a file, a log or a commit.
5. **Stage explicit paths.** Never `git add -A` or `git add .`, least of all in a copy where a package install or build ran.

TrackAI-wide hard rules (from Task2–Task6):

6. **Raw customer content is sensitive IP.** Raw prompts, responses, tool payloads and commands are never returned by ordinary APIs, never logged, never put in documentation and never in non-synthetic fixtures. The one deliberate exception is Task5's raw reveal: off by default, tenant-bound, limited to approved administrator/auditor roles, explicitly requested per event, audited and sent `no-store`. Do not widen it or add another path without a founder decision.
7. **Honest states.** Keep observed vs audited, detected vs blocked, zero vs `Unavailable`, exact vs confidence-based linkage distinct. Monitor-only evidence is never described as prevention.
8. **Task2 owns lifecycle metric semantics** (Generated, Committed, In-PR, Merged, Production, Reworked, Churned). No other Task redefines them without an explicit cross-Task change.
9. **The server is authoritative.** Client filtering, disabled buttons and previews never replace tenant-bound server enforcement and audit.

## 3. Git workflow

Each agent works in its own **git worktree** on its own branch, never in the main checkout and never on `main`.

| Item | Convention |
|---|---|
| Main checkout | `~/AIProjects/TrackAI-v1` (on `main`; agents never commit here) |
| Worktree | `~/AIProjects/TrackAI-wt/<name>`, made with `make worktree M=<name>` |
| GitAI worktree | `~/AIProjects/TrackAI-wt/<name>-gitai`, made with `make gitai-worktree M=<name>` (from the TrackAI main checkout) |
| Task ID | `Task<N>`; a session within it `Task<N><letter>` (`Task15a`, `Task15b`) |
| Branch | `task/<name>`, where `<name>` is `<ID>-<slug>` (`task/Task15a-attesta-chain`); GitAI: `task/<name>-gitai`; docs-only: `docs/<name>` |
| Commit message | `<ID>: <imperative summary>`; docs-only sessions use the session name (`adopt-agent-kit: …`) |
| PR title | `[<ID>] <Task name>` |
| PR body | The session's handoff file |

Commit at each stage. Rebase on `main` before handing off. Never force-push a branch another agent may have pulled. Pre-kit branches (`feature/…`, `codex/…`) keep their names.

**Two repositories, separate PRs.** A Task that changes both TrackAI and GitAI runs them as separate sessions with separate branches and PRs, joined by named checkpoint SHAs in the handoffs. In GitAI, review against `origin/main` (the fork), never `upstream/main`.

## 6. Testing

- **Unit tests** run with no external services (no database, no network): `npm test` (root; runs `apps/api`'s `node:test` suite, about 150 tests in a few seconds).
- **Prefer the real thing in-process over mocks.** Drive the real API, the real repositories and the real services in-process where you can; mock only what cannot run locally, and say what was mocked.
- **An optional toolchain that is absent makes a test skip, never fail** (the Python semantic model, Docker, a GitAI build).
- **Integration tests are founder-owned, agent-assisted.** If behaviour can only be proven against a real dependency (database triggers, RLS, concurrency, volume, a real agent or host), propose tests with IDs `IT-<ID>-NN`, kept out of `npm test`, and runnable through `scripts/it-db.sh`. Tests that span several Tasks are listed as future `IT-M<n>-NN` entries, not written alone. Codex's existing `verify:*` scripts and `E<N>-*` evidence gates keep their names; new ones are registered in the integration test registry too.
- **Every handoff has an "Integration test impact" section**, even if it says "none": tests added, the exact command, prerequisites, blocking or non-blocking (and for what), and status. Update the matching rows of the integration test registry in `docs/plan/STATUS_BOARD.md`.
- **Shared test fixtures are frozen.** Ask before adding or changing one.

Toolchain:
- Node 20+ (CI uses 20). One `npm ci` per worktree; run tools through `npm run …` / `npm exec`, never a global install.
- Integration databases: `scripts/it-db.sh <command>` starts a throwaway PostgreSQL 16 with pgvector on a free port (Docker image `pgvector/pgvector:pg16`, or local binaries with the pgvector extension), exports `DATABASE_URL`, sets `TASK5_EPHEMERAL_DATABASE=1`, `TASK6_EPHEMERAL_DATABASE=1` and throwaway encryption keys, applies the migrations, runs the command, then removes the database. Example: `scripts/it-db.sh npm run verify:task5-graph-live -w apps/api`. A verifier that insists on a database name sets it: `IT_PG_DATABASES=trackai_task6_security_live IT_PG_EXPORTS=DATABASE_URL=trackai_task6_security_live scripts/it-db.sh npm run verify:task6-route-live -w apps/api`.
- Older runbooks use a fixed Docker port (`55432`) and a test auth server on `54321`; they still work for the founder's walkthroughs, but new commands for agents and the founder use `scripts/it-db.sh` and never a fixed port.
- GitAI: `task test`, `task build`, `task lint`, `task fmt` (GitAI's own `AGENTS.md` governs inside that repo).

## 9. Project gotchas [PROJECT SLOT]

These have already caused bugs or near-misses. Do not reintroduce them.

1. **Several similarly named checkouts exist** (Codex folders, the upstream GitAI clone, the fork). State the absolute directory and repository before any command; the wrong one can look healthy.
2. **GitAI review base is the fork's `main`.** Comparing against the upstream or another local clone pulls in older Task2/4/5 work.
3. **Tenant isolation is application-enforced.** Tenant-owned tables are read and written through `withTenant()` (`apps/api/src/core/db/tenant.ts`); RLS is enabled with no browser policies, so direct Supabase reads from the web are denied. A new table gets both.
4. **Migrations are dry-run first.** Generate, inspect, apply on a throwaway database, then the persistent and fresh-schema gates. Never edit a merged migration.
5. **Live verify scripts refuse non-ephemeral databases** unless `TASK5_EPHEMERAL_DATABASE=1` / `TASK6_EPHEMERAL_DATABASE=1` is set; `scripts/it-db.sh` sets them for its throwaway database only. Never set them against a database you care about.
6. **Prove which database a live daemon has open** before a GitAI live test, and isolate test runtime databases and configuration from the normal user daemon.
7. **GitAI performance:** Trace2 remains the Git integration source; never wrap Git, never add per-commit/file/object/ref Git spawns or unbounded Git work, and add nothing to the latency-sensitive ingestion path without measured evidence.
8. **A green command is not a correct metric.** Lifecycle changes need the Lifecycle Lab's controlled scenarios, not just unit tests.
9. **Activation is fail-closed and tenant/repository-bound** (Task6). Off, disconnected, expired and restarted states produce no finding and no upload.
10. **Destructive and revocation actions are dry-run first, with exact scope stated**; never rotate or revoke a credential without an explicit confirmation step.
11. **Task6 support boundary.** Only the observe-only OpenCode terminal/TUI route on macOS (`AC-CLI-03`) is validated. D6.1 (Policy-owned, signed, machine-bound activation) blocks production activation; D6.2 (Linux, Windows, WSL, other agents and surfaces) blocks any wider route or platform claim. Never describe more than that.
12. **Task5 raw reveal stays default-off and restricted** (rule 6): tenant opt-in, approved roles, per-event request, audit, `no-store`.
13. **Sandbox failures are not product failures.** In an agent sandbox, `npm ci` can end with npm's "Exit handler never called" while the log shows DNS denial, and a local PostgreSQL can fail with `shmget`. Classify these as sandbox failures, and retry only that exact command with command-scoped permission (or hand it to the founder); do not change code or configuration to get around them.

## 10. Style [PROJECT SLOT]

- TypeScript `strict` in both apps. The API targets ES2022 and builds to CommonJS; the web app targets ES2017 with ESNext modules (Next.js). API tests use `node:test` via `tsx` and live beside the code (`*.test.ts`), registered in `apps/api/package.json`'s `test` script; the web app has no unit tests yet.
- Database access: Drizzle. Some existing routes query directly (`features/telemetry/read.routes.ts`, `features/scm/scm.routes.ts`); **new code puts queries in the feature service** and keeps route handlers thin. Tenant-owned access goes through `withTenant()`.
- Routes (`apps/api/src/index.ts`): `/health` (unauthenticated); `/api/v1/webhooks/*` (raw body, provider signature verification); `/worker/*` (machine-authenticated GitAI uploads, including `/worker/security` and `/worker/evidence`); `/api/*` (Supabase JWT plus tenant middleware); `/api/admin/*` (administrators).
- HTTP responses with sensitive data send `Cache-Control: no-store` and safe error codes, never raw values.
- Comments explain why. Docs in plain language, short tables, stable IDs.
- Existing trackers keep their legend (🟢 ✅ / 🟡 ◐ / 🔴 ☐ / ⚪ —); new documents use §11's three symbols (✅ = 🟢 ✅, 🟡 = 🟡 ◐, ⬜ = 🔴 ☐, n/a = ⚪ —).

## 11. Status symbols, founder to-dos, and chat formatting

Status lives in `.md` files (handoffs, `docs/plan/STATUS_BOARD.md`), with three symbols:

| Symbol | Meaning |
|---|---|
| ✅ | Done for the stated scope, verified live where that is required |
| 🟡 | Partial, or done but waiting on a founder run or other live gate |
| ⬜ | Not done or not tested |

Everything else is plain words:
- Founder to-dos start with **FOUNDER:** and include the exact commands.
- Say "blocking" (and name what it blocks) or "non-blocking" for every integration test and founder to-do.
- Use "n/a" for deferred or not-applicable items.
- "Verified in the agent sandbox" is 🟡, not ✅. Only the founder's own run, or a live environment, makes an integration item ✅.
- When a status changes, update it in place; strike resolved founder to-dos through (`~~…~~`) with the date.

**In chat replies** keep formatting light and use no status symbols.
- **Commands for the founder go in one `bash` block**, in run order, with short `# comments` for sections and expected results, so it pastes at once. Never split a sequence across blocks or put commands in a table. Every block starts with the absolute directory (`cd ~/AIProjects/...`).
- **The founder uses the terminal, not the GitHub web UI.** Give every push, PR and merge as `git` / `gh` commands. Always pass `--head <branch>` to `gh pr create`: the founder often runs the block from the main checkout on `main`.
- One recommended path, not a menu, unless the decision is genuinely the founder's.
- A data table goes inside a `text` block so it copies as plain text.
- Plain, beginner-friendly language; lead with the result; never ask a question the repository can answer.

## 12. Session protocol (every agent)

### 12.1 Where you may work
- **Only under `~/AIProjects`.** Do not read or write anywhere else on the founder's machine: no `~/.ssh`, no global git config, no `~/Documents` (the old Codex folders there stay untouched), no system packages. Caches your tools create on their own are fine.
- **Read-only exceptions:** agent-kit at `~/dev/agent-kit` and the reuse source `~/dev/sushicorp` may be read, never written.
- **Your worktree is your whole world.** Never edit another agent's worktree. **The main checkouts `~/AIProjects/TrackAI-v1` and `~/AIProjects/git-ai` are read-only**: never `checkout`, `reset`, `stash`, commit or `worktree prune` there.
- **Git identity:** `mahamannu-ux <mahamannu@gmail.com>`, set per command or per worktree (`git config user.name …` inside the worktree), never globally.
- **Codex:** the Codex project points at `~/AIProjects/TrackAI-v1` and its worktree root is `~/AIProjects/TrackAI-wt` (Settings > Worktrees). **Check where you are first** (`pwd`): if you are not under `~/AIProjects/TrackAI-wt/`, stop and tell the founder. If you start on a detached HEAD or a `codex/...` branch, run `git switch -c task/<name>` (or `git branch -m task/<name>`) before your first commit. Keep the default sandbox (workspace-write); do not ask for full access. The founder pulls `main` before a session (Codex does not fetch when it creates a worktree), so your base is current.
- **Muse in OpenCode (or any CLI agent):** the founder creates your worktree with `make worktree M=<name>` and starts you in it (`cd ~/AIProjects/TrackAI-wt/<name> && opencode`); work only there. OpenCode's own per-chat worktrees stay off; permission prompts stay on.
- **Claude:** cloud sessions move commits through git bundles in `~/AIProjects/_bundles` and never create worktrees from the linked shell (`CLAUDE.md`).
- More on each agent's setup and failure modes: `~/dev/agent-kit/agents/AGENT_PROFILES.md`.
- Ask before any command that writes outside your worktree.

### 12.2 Start of session
1. Read this file, your Task's tracker and the status board in `docs/plan/STATUS_BOARD.md`, the Task primer (`docs/plan/primers/`), the remaining plan, and the handoffs your prompt names.
2. Give the founder a **one-line effort estimate** against T6, and say if the work should be split.
3. **Ask before touching a shared surface:** `apps/api/src/core/db/schema.ts`, a new migration, `package.json` / `package-lock.json`, `apps/api/src/index.ts`, `apps/api/src/core/middleware/`, `.github/workflows/`, another Task's tracker, the GitAI↔TrackAI upload contracts, a new top-level dependency, or a file outside your Task's directories. Your prompt may pre-approve specific ones. Never touch the frozen paths (§1).
4. Then work without check-ins: interfaces first (§5), commit at each stage.

### 12.3 Testing split
- **Your sandbox:** unit tests, plus each integration test you add, once, at small size.
- **The founder's machine:** full and volume integration suites, real agents, browsers, tenants and machines. You write the exact commands; the founder pastes back only failures and safe summary lines.
- **Never poll a long run.** Hand it to the founder.
- **Integration databases:** every integration run goes through `scripts/it-db.sh` (a throwaway database on a free port, removed afterwards). Never name a fixed port in commands for the founder, and never assume a long-running local database is the one listening.
- **One independent review** before the handoff (Claude: a review subagent; Codex: a fresh thread or `/review`; others: re-read the full diff as a reviewer). Fix what it finds or say why not in the handoff.

### 12.4 How you talk to the founder
The founder reads chat on a phone or between meetings. Every final reply has this shape:
1. **One or two sentences:** what is done, and whether anything blocks. At close-out add `Effort: about <actual>× T6 against an estimate of <estimate>×`, and the main reason if it ran over.
2. **Decisions the founder should know**, one line each (only those that change behaviour, a shared file, or scope).
3. **Questions that genuinely need the founder**, each with your recommended answer.
4. **Exactly one `bash` block** with everything to run, in order: checkout, install, unit tests, integration tests, then, under `# after the cross-agent review`, `git push` and `gh pr create --base main --head <branch> --title "[<ID>] <name>" --body-file <handoff> --repo mahamannu-ux/TrackAI-V1` (or `--repo mahamannu-ux/git-ai`).
5. **Exactly one `text` review request**, which the founder pastes as is to the reviewer (§12.6). It names the branch, the commit, the session and Tasks, and anything the reviewer needs to reach the code (where it is checked out, which runs already passed). Repeat it with the new commit after fixing review findings.
6. Nothing else: no recap of steps, no status symbols.

Mid-session messages follow the same rule: short, and a question only when you are blocked.

### 12.5 Close-out checklist
- [ ] Definition of done (§7)
- [ ] Handoff (§8) with Integration test impact and Effort; the actual also goes into the remaining-plan table
- [ ] Status board and integration test registry rows updated (🟡 sandbox, ⬜ founder run)
- [ ] All work committed on the branch; working tree clean
- [ ] Final reply in the §12.4 shape, including the review request
- [ ] Cross-agent review answered: fixes committed, or why not
- [ ] After the founder reports his runs: statuses to ✅ in a last commit on the same branch, before he merges

### 12.6 Cross-agent review (before the founder pushes)
A different agent reviews every finished session:
- **Claude's branches:** Codex or Muse.
- **Codex's and Muse's branches:** the standing **TrackAI-Orchestrator** Claude chat.
- **When Codex leads a Task and hands a piece to Muse** (§12.8): Codex reviews Muse's branch; the orchestrator reviews Codex's.

The founder pastes the author's review request and nothing else; the reviewer reads `docs/agents/CROSS_REVIEW_PROMPT.md` from `main` and follows it. The reviewer is **read-only** (never commits to the author's branch), checks the branch against this file, the spec and the handoff, runs the gates, and returns **ready to push** or **fix first** with a numbered list of fixes the founder pastes back. The founder pushes only after "ready to push". Finding nothing is a valid outcome.

### 12.7 Naming sessions and the standing chats
- **Name a session after what it handles** (`Task15a-attesta-chain`), never "session A/B". Its prompt is `docs/prompts/NEXT_CHAT_<name>_PROMPT.md`, its branch `task/<name>` (or `docs/<name>`), its handoff `docs/handoffs/<name>_HANDOFF.md`.
- **Standing chats** do no product code, and restart from their prompt whenever they grow long, because the repository holds the state:
  - **TrackAI-Orchestrator** (`docs/agents/MANAGER_PROMPT.md`): plans Tasks, writes Task primers and session prompts, answers non-Claude agents, reviews their branches, keeps the lessons table and the status board.
  - **FounderQA** (the founder's own chat for product and architecture questions; not set up by the kit here).
- **Non-Claude agents:** when you need a decision, write the question so it can be pasted to TrackAI-Orchestrator (or to the lead Codex thread, §12.8) as is: what you are deciding, the options, your recommendation.

### 12.8 Task start, agent choice and Codex as lead [TrackAI addition]
- **Task primer first.** Before a Task's first session prompt, the orchestrator writes `docs/plan/primers/<TaskN>_PRIMER.md` from `docs/templates/TASK_PRIMER_TEMPLATE.md`: every wave and subtask in plain, jargon-free language with a customer example, what it costs, and whether it could be simplified or deferred. The founder marks each one keep / simplify / defer / reorder; only then is the Task split into sessions.
- **Choosing the agent for a session:**
  - **Muse** by default when every decision can be made upfront and the work is well bounded (it is faster and free).
  - **Codex** when the work needs long evidence and verification back-and-forth with the founder (live agents, real machines, tenants, browsers), or deep context on code it wrote.
  - **Claude** for cross-cutting design, UI/UX, security-critical cores and integration-heavy work.
- **Codex as lead when Claude is not available.** The founder may start a Task with Codex directly. Codex may then hand a bounded piece to Muse: it writes the Muse prompt from `docs/templates/NEXT_CHAT_PROMPT_TEMPLATE.md` with every decision made, pre-approved files and a "Port from" section, and it reviews Muse's branch with `docs/agents/CROSS_REVIEW_PROMPT.md`. Muse's piece gets its own branch from `main` and its own PR; if it depends on Codex's interface, that interface lands first as a small PR (§5). Codex follows `docs/agents/MANAGER_PROMPT.md` for these duties.
