# TrackAI vision (founder, as given)

*Recorded 2026-10-07 by TrackAI-Orchestrator, unedited. Part 1 is the TrackAI Claude project description; part 2 is the founder's chat message of 2026-10-07. Edits only with the founder's OK; he will extend it.*

## 1. High-level vision (short version)

TrackAI is an AI Code Provenance, Security, Attribution and Engg Productivity Product, which is already partially done by Codex (Task 2 to Task 6.a done and merged). It is inspired by and built on top of git AI (https://github.com/git-ai-project/git-ai ; official Enterprise website at https://usegitai.com/), entire.io (https://entire.io/ ; not built on top of this, but entire.io inspires Task5) and Numbat (https://github.com/perplexityai/numbat). Numbat inspires Task 6.a.

**Provenance:** There is no task for this yet in the Roadmap. This will be Claude's first task. This task/feature will be called Attesta. This will be similar to SigStore/Rekor based signing done in SushiCorp. Details to follow.

**Security:** Coding Agent security will be provided by Numbat implementation through Task6.a. Currently only Monitor mode is supported. Later a Policy subsystem as defined in Task6.b (or a possible re-architecture based on Claude's input and learnings from agent-kit) would also be implemented.

**Attribution:** Identifying which Code is AI vs human-authored. This is done through Task2. Task13 will expand through further work on Task13. Providing useful observability metrics.

**Engineering Productivity:** Task2 + Task5. Task2 gives valuable insights on how much Code is generated by AI per Repo/PR/Model/Developer. How much rework is based on AI-generated code. What is the churn? Task5 provides Entire.io's offering, i.e. ability to visualize prompt to commit/PR (and in reverse), find similar work done before, identify non-performing Tool calls and much more.

## 3. Positioning notes (founder, 2026-10-08)

- TrackAI doesn't really need future Git AI updates. The fork's changes (59 files and more to come) are TrackAI's version to maintain. The Git AI open-source repo does not include the enterprise parts (server, communication, services, dashboard) that TrackAI has already built.
- TrackAI provides AI attribution data, insights and metrics across machines (Mac, Windows, Linux), coding agents, models, IDEs and desktop apps (such as Claude and Codex). An OpenAI-owned Git AI will likely provide that too, but probably just for OpenAI's models and coding agents.
- AI code attribution by itself is a pillar, but the real value comes from the **Security and Provenance** layers. TrackAI's target customer is primarily the **CISO**, then the engineering team and the CIO.
- TrackAI has added Entire.io's feature set (not yet where it should be). Entire.io is a competitor of Git AI; Git AI does not offer Entire.io's features.
- **Audit and the auditor** are a subtask or Task of their own. Audit information today covers Task6.a security findings and Task4 admin actions (machine grants and revocation, credentials). D6.1 signed activation, Task6.b signed policy bundles and Task14 signed artifacts have no audit events yet but will. There is no API, invitation or report surface like SushiCorp's; some of it belongs to Task11 (API/SDK). Not yet clear.
- Attesta's shared trust layer (signer, key hierarchy, rotation, revocation) is owned by Attesta and reused by D6.1, Task6.b and Task14.

## 4. Security through Numbat, and a modular product (founder, 2026-10-16)

*Recorded by the Task19 lead at the founder's request. Supersedes the "Security" paragraph in §1 and the Task6.a note in §2.*

- **TrackAI provides coding-agent security through Numbat** (https://github.com/perplexityai/numbat, Apache-2.0). Security is a **first-class subsystem and offering**, not a side feature of attribution.
- **Adopt Numbat the way TrackAI adopted Git AI:** take the engine, its rules, its agent and platform adapters and its test framework as they are, and add what it lacks: enterprise integration (fleet distribution, policy management, central ingestion, tenant isolation, audit, signed evidence, the CISO's console). The Task6.a approach, re-implementing a few Numbat rules inside TrackAI's own client, is replaced. Whether TrackAI keeps a fork or a synced clone of Numbat is a minor decision for the plan.
- **Numbat can also feed observability** (agent activity, tool calls, approvals, agent inventory), where it fills gaps Task13 would otherwise build custom, so long as TrackAI's raw-content rules hold.
- **The product is modular.** A customer may buy one part or any combination:
  - Security;
  - Code attribution and engineering productivity (Task2, Task5);
  - Attesta (signed provenance), with code, with security, or with both;
  - all of them.

  The architecture must allow each part to be enabled, sold, deployed and operated on its own, and to work better together.
- **Reference material:** the founder's research primers in this folder (`numbat-architecture-capability_reference_primer.md`, `numbat_enterprise_blueprint_primer.md`, `numbat_server_architecture_primer.md`, `numbat_observability_blueprint_primer.md`). They are input, not authority: Numbat's own code and docs are the source of truth. The lead's review that checks the primers against Numbat is `docs/plan/NUMBAT_ADOPTION_REVIEW.md`.

## 5. Intent and decision review (founder, 2026-10-23)

*Recorded by TrackAI-Orchestrator at the founder's request. Working name **IDRES** (Intent & Decision Review/Evidence System); final name open (candidates below). Grows Task5; planning slot to be set by the founder (Task5 expansion after Task13's cloud capture).*

**Marketing line (founder):** "Code reviews expire in 2027. IDRES replaces code reviews."

**Idea.** When most code is written by agents, reviewing every line stops scaling. The reviewer instead approves the *intent* (what was asked, why, what was decided) and checks that the code matches it, with signed evidence of who approved what. Every feature below is enabled from the data TrackAI already captures or will capture (Task2 attribution, Task5 evidence graph and semantic search, Task13 surfaces including cloud sessions, Attesta signing):

1. **"Why does this exist?" at every level:** line, function, file, PR and release, answered with a short intent summary linked to the sessions, prompts, decisions and approver.
2. **Intent drift:** flag a PR whose code does not match its stated intent, ticket or spec; a CISO-relevant signal.
3. **Decision records:** decisions made by agents and humans during sessions ("chose library X because Y") pulled into a searchable per-repository record.
4. **Session replay in review:** the reasoning trail beside the diff.
5. **"Has this been done before?":** similarity across past sessions and PRs (Task5 semantic search).
6. **Signed intent:** Attesta statements carry an intent digest and the approver, so the "why" and the approval become evidence. Neither Git AI nor Entire does this.
7. **Cross-agent and cloud sessions:** the same view whether the work ran on a laptop or in a cloud sandbox (`STRATEGY_CLOUD_AGENTS_2026-10-22.md`).

**Why it sells to the CISO.** Change-management controls (SOC 2 CC8.1, ISO 27001 A.8.32) require evidence that changes were authorised and reviewed. IDRES keeps a human approval but moves it to intent, and produces stronger evidence than a "LGTM" on a diff nobody read. Raw prompts stay under rule 6: summaries and digests by default, raw reveal only through Task5's governed path.

**Competition.** Entire (Thomas Dohmke, former GitHub CEO; $60M seed, February 2026) captures sessions as Git checkpoints, links commits to them, and generates intent/outcome summaries (`entire explain`); it covers Claude Code and Gemini CLI. Git AI focuses on attribution. Code-to-intent linkage is therefore not unique; the difference is cross-agent and cloud capture, intent drift, decision records and signed approval.

**Name candidates (orchestrator):** IDRES (working); **Intent Review**; **WhyTrail**; **IntentProof** (fits the portfolio's "…Proof" family).
