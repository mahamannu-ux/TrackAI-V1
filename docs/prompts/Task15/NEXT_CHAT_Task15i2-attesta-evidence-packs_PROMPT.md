## 2. Scope
### 2.1 Lead decisions
1. **Pack format v1 (contract, additive, lead-approved):** new `docs/contracts/attesta/evidence-pack.md` and `evidence-pack-v1.schema.json`. One JSON document (RFC 8785 bytes) written through `EvidenceExportSink`:
   - `manifest`: `{format: "https://trackai.dev/attesta/evidence-pack/v1", pack_id, tenant_id, scope: {repository_id|null, from, to, mode}, chain_range: {from_seq, to_seq, head_record_hash}, generated_at, counts, sections: {<name>: sha256 of that section's JCS bytes}}`.
   - `records`: the tenant chain segment covering the scope, each `{seq, canonical_record, record_hash, prev_hash}` (redaction per item 2), so a verifier recomputes every hash and proves the segment gap-free.
   - `statements`: in-scope `{statement_canonical, envelope}`; `anchors` and `anchor_batches`: the rows for in-scope records (EV-2 v1 proofs, TSA tokens); `trust`: `{root_documents, keyset_documents (from version 1), anchoring_keys (SPKI + root entry), rekor_log_key, rekor_log_index_offsets, tsa_anchors}` (all public); `verification_hint`: the pinned root keyids the pack expects (the verifier must take its pin from the user, never from the pack alone; say so in the contract); `reports: []` (reserved for Task15i3's period-report documents); `verifier: null` (A15.10 fills it later).
   - **Pack signature (RP-1):** a DSSE envelope, payload type `application/vnd.trackai.evidence-pack+json`, over the JCS of `{pack_digest: sha256 of the pack JCS bytes, manifest}`, signed with the tenant's active `statement` key through `inventorySignerResolver(pgTrustStore(db), await adaptersFromEnv(), trustConfigFromEnv())` and `signVerified`; between a key's `activate` and the next `publish` the resolver throws `SigningUnavailable`, so the job ends `failed` with a retryable code and says so, stored and shipped next to the pack. **Not chained** in phase 1: everything inside is already chained and anchored; the signature says who exported what, when. Say so in the contract.
   - Bounds: at most 50 000 statements per pack (else 400 `ATTESTA_API_INVALID_QUERY`); records not yet anchored ship with `anchor_status: pending` and the manifest says how many (never presented as fully anchored, api.md).
2. **Per-repository completeness (checkpoint question, recommendation below):** a pack scoped to one repository proves "nothing in this repository was left out" only with every record's `canonical_record` in the segment, which reveals other repositories' record metadata (repository UUIDs, subject shas, kinds, digests; never statements). Two modes: `full` (default: completeness provable) and `repository_only` (out-of-scope records reduced to `{seq, record_hash, prev_hash}`; the chain links still verify, but in-scope completeness is reported `not_provable` and the verifier exits 2 for that claim). **Recommendation:** ship both, default `full` for the tenant's own and its auditors' use, `repository_only` for outsiders; no per-repository Merkle commitment in phase 1 (it would change the ledger record format).
3. **Tables (migration `0020`, after 15l2's `0019`; verify the number):** `attesta_evidence_packs` (tenant-owned: `id`, `tenant_id`, `idempotency_key`, `scope` jsonb, `mode`, `status` (`queued` · `running` · `ready` · `failed`), `requested_by`, `request_id`, `pack_digest`, `storage_reference`, `bytes`, `signature_envelope`, `error_code`, `lease_until`, timestamps; unique `(tenant_id, idempotency_key)`; status moves only forward; RLS, composite keys, `withTenant`) and `attesta_anchor_resumes` (append-only: `tenant_id`, `batch_id` FK to `attesta_anchor_batches`, `actor`, `reason`, `request_id`, `created_at`; guard: the batch's latest attempt failed with a terminal code).
4. **Routes** (in `attesta.routes.ts`, AP-1 conventions from `http.ts`): `POST /api/attesta/evidence-packs` (body `{repository_id?, from, to, mode?}`, `Idempotency-Key` header required, `^[A-Za-z0-9._-]{8,64}$`; same key and scope → the same job, same key and another scope → 409 problem; 202 `{id, status}`), `GET /api/attesta/evidence-packs/{id}` (status, counts, `pack_digest`, and when ready the content path), `GET /api/attesta/evidence-packs/{id}/content` (streams the pack and its signature as `application/json`, `no-store`, `Content-Disposition: attachment`, audited). Another tenant's id → 404 like an unknown one. New action `attesta.export` for all three, allowed for `tenant_admin` and `tenant_auditor` (an auditor's job is to take evidence; every export and download is audited); add the routes to the AU-1 sweep lists.
5. **The job:** `evidence-pack-service.ts` `runEvidencePack(db, deps, packId)`: claim (`queued` → `running` with a 10-minute lease; an expired lease is retaken), read the segment in one repeatable-read transaction, build, sign outside any transaction, write through the sink, then `ready` with digest, reference and bytes; any failure → `failed` with a code, never a partial pack. Started in-process after the 202 (`setImmediate`) and by a CLI `npm run attesta:pack -w apps/api -- --run-queued` for recovery; production scheduling is Task14's. Two identical requests never build twice. Audit rows: `attesta.export.request`, `attesta.export.download` (request ID, scope, mode, counts; no digests of customer content beyond the pack digest).
6. **Real keys in `/verify`:** wire `publishedKeysFor(pgTrustStore(db), tenantId)` (`.keys`) into `VerifyKeySource` (`createAttestaRouter({ keys })`), and pass `anchorKeyWindows: await platformKeyWindows(store, 'anchor', trustConfigFromEnv())` with the anchor material (never a bare SPKI list in production; Task15l2 handoff "Integration notes"), so a healthy chain verifies `ok` with signatures and anchors checked; keep the seam for tests. Packs take `trust.root_documents` / `keyset_documents` from the same `publishedKeysFor` result and the anchoring keys from `platformKeyWindows`. Pass each record's anchor time as `timeEvidence` only where `verify-chain.ts` supports it; if it needs a change to accept `timeEvidence` per record (retired-key statements), make that change additively and say so.
7. **Anchor resume (Task15f2 decision):** `npm run attesta:anchor-resume -w apps/api -- --tenant <uuid> --batch <batch_id> --actor <name> --reason <text> [--confirm=RESUME]`: dry-run by default (prints the batch, its terminal code and the record count), applies one `attesta_anchor_resumes` row and one `security_audit_events` row; `anchor-worker.ts` treats a stopped batch with a resume row newer than its last terminal failure as retryable again (one more attempt per resume row). No route (operators only).
8. **Production build resolver (Task15l2 integration note):** `attesta-build-cli.ts` still builds only with `devSignerResolver`; its production branch becomes `inventorySignerResolver(pgTrustStore(db), await adaptersFromEnv(), trustConfigFromEnv())` (development unchanged). A unit test proves production never reaches the dev resolver.
9. **Contract tidy-ups from the Task15i handoff (additive):** `errors.md` §API gains `ATTESTA_API_UNAUTHENTICATED` (401), `ATTESTA_API_UNAVAILABLE` (503) and `ATTESTA_API_CONFLICT` (409, idempotency key reused for another scope); `api.md` names verify report version 2 and the content route. ## Lessons so far
- **Task15l2 (Claude):** a test fixture with a fixed time and certificates dated from `Date.now()` became a time bomb; give every fixture one injected clock.
- **Task15i (Claude):** a malformed `%`-encoding in a path gave a 500; validate every path and header before it reaches the store. The route sweep must cover middleware layers.
- **Task15l (Claude):** run the review subagent on a contract before anything is bundled; treat unsigned values as attacker-controlled (here: `verification_hint`, pack `scope`).
- **Task15f2 (Claude):** exercise the real env path once in the live test.
- **SushiCorp S4 (kit lessons):** determinism bugs came from the clock source and from counting live rows; build packs only from stored bytes, with the database clock.
