## 2. Scope
### 2.1 Lead decisions (confirm or change at checkpoint 1)
1. **Two hierarchies, one format.**
   - *Platform:* an **offline platform root** (one or more keys, never on a server; a key file in dev) signs a **trust root document** listing the platform's online keys, each with one **purpose**: `anchor` (Rekor entries), `activation_lease` (D6.1), `fleet_config` (Task9), `policy_bundle` (Task6.b), `release` (T14.7), `tenant_keyset` (see below). GitAI and auditors pin the root keyid(s) at install or in the verifier.
   - *Tenant:* each tenant's **statement keys** (purpose `statement`) live in the tenant's own KMS (no custody, TASK15 §2 decision 3); a tenant administrator registers them. The tenant's **key set document** lists them with validity and status and is signed by the platform `tenant_keyset` key, so a verifier can check "this key was registered for this tenant from then until then" offline.
2. **Document format:** a DSSE envelope (reuse `dsse.ts`), payload type `application/vnd.trackai.trust-root+json` or `application/vnd.trackai.keyset+json`, payload in RFC 8785 JSON: `{ _type, scope ("platform" | tenant UUID), version (integer, strictly increasing per scope), issued_at, expires, previous (digest of the previous document or null), threshold (root documents only), keys: [{ keyid, purpose, spki_der_b64, not_before, not_after, status ("active" | "retired" | "revoked"), revoked_at?, revocation_reason? ("superseded" | "compromised"), compromised_since? }] }`. A new root document must be signed by `threshold` keys of the **previous** root (TUF-style root rotation; phase 1 threshold 1, the format supports k-of-n). Key sets and the platform online-key list are signed by a currently valid key of the right purpose under the current root.
3. **The verifier** (`trust-verify.ts`, pure, no database, no network): `verifyTrusted(input) → { status: 'verified' | 'rejected' | 'unavailable'; code; keyid? }`, exactly Task9's three states. Input: the signed bytes and payload type, the DSSE envelope, `{ purpose, audience (tenant UUID or "platform"), signedAt, timeEvidence? }`, and a `TrustState` (pinned root keyids, the documents held, the highest version seen per scope, `now`, allowed clock skew). Rules, each a test:
   - Root chain verifies from the pinned root by threshold, version by version; a lower version than the highest seen is **rejected** (rollback); a missing or expired document is **unavailable** (never verified); a document past `expires` plus skew is unavailable.
   - The signing key must be listed for exactly this purpose and audience; another purpose or tenant is rejected.
   - `signedAt` must fall in `[not_before, not_after]`; `retired` and `revoked/superseded` keys verify only for `signedAt` before `revoked_at` (rotation overlap).
   - `revoked/compromised`: a signature is verified only if **independent time evidence** (an anchored TSA `gen_time` or Rekor `integratedTime`, passed as `timeEvidence` and itself already verified) proves it existed before `compromised_since`; a self-claimed `signedAt` from a compromised key is never enough (rejected).
   - Revocation information that cannot be obtained is UNKNOWN → unavailable; **UNKNOWN is never CLEAN** (AGENTS.md §9 item 19; catalog TR-1).
   - Production refuses to verify without a pinned root (`ATTESTA_TRUST_ROOT_NOT_PINNED`).
4. **Contract (checkpoint-2 PR, additive, lead-approved):** new `docs/contracts/attesta/trust.md` (hierarchy, purposes, document format, verification order, rotation and revocation procedures, the consumer interface), `docs/contracts/attesta/trust-document-v1.schema.json`, an additive `## Trust (A15.12)` section in `errors.md` with the codes (proposal: `ATTESTA_TRUST_ROOT_NOT_PINNED`, `_DOCUMENT_SIGNATURE_INVALID`, `_THRESHOLD_NOT_MET`, `_DOCUMENT_EXPIRED`, `_DOCUMENT_UNAVAILABLE`, `_ROLLBACK`, `_KEY_UNKNOWN`, `_PURPOSE_MISMATCH`, `_AUDIENCE_MISMATCH`, `_KEY_NOT_VALID_AT`, `_KEY_REVOKED`, `_REVOCATION_UNKNOWN`, `_SIGNATURE_INVALID`); `apps/api/src/features/attesta/trust-contract.ts` marked `[CONTRACT - FROZEN]` with the types and `verifyTrusted` signature (stub that throws until the implementation lands); and **vectors** `apps/api/src/features/attesta/vectors/trust/*.json` (good chain, root rotation, each failure above) generated by a script from fixed test keys, so GitAI's Rust verifier can prove the same answers.
5. **Inventory (migration, after 15f2):** `attesta_platform_keys` (platform-owned; no tenant column; public material only: keyid, purpose, adapter name, `credential_ref` (KMS resource name, never a secret), SPKI DER, validity, status, revocation fields), `attesta_tenant_keys` (same columns plus `tenant_id`, purpose `statement` only, composite tenant keys, RLS on with no policies, `withTenant`), `attesta_key_events` (append-only: register, activate, retire, revoke, publish; actor, reason, key, the document version produced) and `attesta_trust_documents` (append-only: scope, version, digest, envelope bytes; guard: version strictly increasing per scope, `previous` equals the stored previous digest). Guards in the 0017 style (`SECURITY DEFINER`, `search_path = pg_catalog, pg_temp`, UPDATE/DELETE/TRUNCATE raise) except the key status columns, which change only through a guard-checked transition (`active → retired → revoked`, `active → revoked`; never back) with a matching `attesta_key_events` row in the same transaction.
6. **Resolvers:** `inventorySignerResolver(db, adapters)` implements `SignerResolver` (A15.8) from `attesta_tenant_keys` (the one `active` statement key, through `KmsSigner`; none → `null` → `ATTESTA_SIGNER_NO_CREDENTIAL`); `platformSigner(db, adapters, purpose)` returns the active platform key for a purpose, and replaces the production refusal in 15f2's `anchor-env.ts` for `anchor`. `publishedKeysFor(tenant)` returns what `verifyChain` and A15.9 need (current and historical public keys with validity).
7. **CLIs** (`npm run attesta:keys -w apps/api -- <command>`): `register`, `activate`, `retire`, `revoke --reason superseded|compromised [--compromised-since <iso>]`, `publish` (builds the next key set or platform list and signs it with the online `tenant_keyset` key). **Dry-run by default**, exact scope printed, `--confirm=<COMMAND>` plus `--expect=<n>` to apply, one `security_audit_events` row per applied run (AGENTS.md §9 item 10). A separate **offline** tool `npm run attesta:trust-root -w apps/api -- sign` builds and signs a root document from key files on a machine with no database or network, and prints only keyids and the document digest; never PEM.
