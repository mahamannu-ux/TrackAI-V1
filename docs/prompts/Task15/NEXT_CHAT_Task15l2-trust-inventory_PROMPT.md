## 2. Scope (approved)
### 2.1 Decisions
1. **Migration `0019`** (next free number; verify), generated from `schema.ts`, guards by hand in the 0017/0018 style (`SECURITY DEFINER`, `search_path = pg_catalog, pg_temp`, RLS on with no policies):
   - `attesta_platform_keys` (platform-owned, no tenant column): `id`, `keyid` (unique), `purpose` (the six platform purposes and `root` is **not** stored: root keys live only in root documents), `adapter_name`, `credential_ref` (KMS resource name; internal, never in a document or log), `spki_der`, `not_before`, `not_after`, `status` (`registered` · `active` · `retired` · `revoked`), `revoked_at`, `revocation_reason`, `compromised_since`, `registered_at`, `pop_digest`.
   - `attesta_tenant_keys`: the same columns plus `tenant_id`; purpose `statement` only; composite tenant keys; `withTenant` access; partial unique index: at most one `active` key per tenant.
   - **Keyid uniqueness across both tables and all tenants** (a guard): a keyid registered once, for one tenant or the platform and one purpose, can never be registered again (trust.md "Registration").
   - `attesta_key_events` (append-only): `id`, `tenant_id` (null for platform), `key_id`, `action` (`register` · `activate` · `retire` · `revoke` · `publish` · `import_root`), `actor`, `reason`, `document_version`, `request_id`, `created_at`.
   - `attesta_trust_documents` (append-only): `id`, `scope` (`platform` or the tenant UUID), `kind` (`root` · `keyset`), `version`, `digest`, `payload_type`, `envelope` (jsonb as signed), `created_at`; unique `(scope, version)`; guard: version 1 has `previous` null, otherwise `version = max + 1` for the scope and the document's `previous` equals the stored digest of `version − 1` (both read from the envelope payload inside the guard or passed as typed columns the guard checks against the payload).
   - **Status transitions only forward** (`registered → active → retired → revoked`, `active → revoked`, `superseded → compromised` only by a later revoke; `revoked_at` and `compromised_since` never move later), enforced by an UPDATE guard that also requires an `attesta_key_events` row for that key and action in the same transaction (deferred constraint trigger). `spki_der`, `keyid`, `purpose`, `tenant_id`, `not_before` never change; `not_after` never grows. DELETE and TRUNCATE raise.
2. **Registration with proof of possession** (`trust-inventory.ts` `registerKey`): the operator gives `--adapter`, `--credential` and, for tenant keys, `--tenant`. The service reads the public key from the adapter (`SigningAdapter`, verify-before-use), builds a challenge `{_type: "https://trackai.dev/attesta/key-registration/v1", scope, purpose, keyid, nonce (32 random bytes, base64), issued_at}` in JCS, has the key sign its DSSE PAE (payload type `application/vnd.trackai.key-registration+json`) through `signVerified`, verifies it, and stores the row as `registered` with `pop_digest` = SHA-256 of the signed envelope. A keyid already present anywhere → refused (`ATTESTA_TRUST_INPUT_INVALID`-style CLI error naming no other tenant). The signature is never published.
3. **Activation:** a tenant `statement` key: `activate --tenant --keyid [--replace]`; with an active key present, `--replace` retires the old one (`revoked_at` = now) in the same transaction (two events), else refused. A **platform** key never becomes active by CLI: it becomes `active`, `retired` or `revoked` only by **importing a signed root document** that lists it so (`import-root`), so one stolen online credential cannot authorize another key (trust.md "Hierarchy").
4. **Root documents:** `export-root-draft` writes a draft body (current root's keys plus the requested platform-key changes from `registered` rows and `--retire`/`--revoke` flags) to a file for the offline machine; the offline `attesta:trust-root sign` (merged) signs it; `import-root --file` parses it, checks it against the stored chain exactly as `verifyTrusted` does (pinned root from a new `ATTESTA_TRUST_ROOT_KEYIDS` (comma-separated keyids; required in production), threshold, forward-only, `previous`), stores it, and syncs `attesta_platform_keys` statuses to what it lists (a listed key not registered here is refused: register it first). Version 1 bootstraps from the pin.
5. **Publishing key sets** (`publish --tenant | --all-tenants`): builds version n+1 from the stored version n and the inventory (keys that ever became `active`; `registered`-only keys are not listed), checks `forwardOnlyViolation` against version n before signing, signs with the platform `tenant_keyset` key through `platformSigner`, lifetime 30 days (`expires = issued_at + 30 d`), verifies the result with the verifier's own document checks, stores it with a `publish` event. Version 1 for a tenant starts the chain (full history from version 1, trust.md). Weekly scheduling is Task14's; the handoff gives the command.
6. **Resolvers** (`trust-resolver.ts`):
   - `inventorySignerResolver(db, adapters)` implements `SignerResolver` (A15.8): the tenant's one `active` statement key whose `not_after` is in the future, resolved to its adapter and `credential_ref`; none → `null` (`ATTESTA_SIGNER_NO_CREDENTIAL`, the builder's existing path).
   - `platformSigner(db, adapters, purpose)` → `{ adapter, credentialId }` for the active platform key of that purpose, only if the **latest imported root document** lists it `active`; else a clear fail-closed error. `anchor-env.ts`: replace the production refusal with `platformSigner(…, 'anchor')`; development keeps the dev key file.
   - `adapters` = `{ kms: KmsSigner built with `kmsCredentialsFromJson` from a file named by a new `ATTESTA_KMS_CREDENTIALS_FILE` (references only, no secrets), dev?: LocalDevSigner (refuses production) }`; adapter name in the row selects one.
   - `publishedKeysFor(db, tenantId)` → `{ keys: Record<keyid, KeyObject>, rootDocuments, keysetDocuments }` (every key the tenant ever had, retired and revoked included, plus the stored documents from version 1). It is what 15i2 passes to `verifyChain` (`keys`) and into evidence packs. Ship it with a unit test against `verifyChain`; do not wire it into routes.
7. **CLIs:** `npm run attesta:keys -w apps/api -- <register|activate|retire|revoke|publish|export-root-draft|import-root|list>` with `--tenant`, `--keyid`, `--reason superseded|compromised`, `--compromised-since <iso>`, `--actor <name>`. Every changing command is **dry-run by default**, prints its exact scope (tenant, keyids, new statuses, document version; never credential refs or key material), and applies only with `--confirm=<COMMAND> --expect=<n>`; each applied run writes its `attesta_key_events` rows and, for tenant-scoped actions, one `security_audit_events` row (`action: attesta.keys.<command>`). Platform actions are audited in `attesta_key_events` only (no tenant to attach them to; Task16 A16.11 picks both up). `list` prints keyids, purposes, statuses and validity only. The CLIs refuse to run with a dev adapter in production.
